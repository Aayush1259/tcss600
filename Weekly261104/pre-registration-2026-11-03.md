## 2. My protocols

Every protocol in my shared pipeline uses the same four parts, computed once per question and cached:
1. Plan: the supervisor reads the question and options, not the record, and writes at most 6 steps.
2. Worker jobs: the worker runs each step on every 6,000 character chunk of the padded record and returns a short answer with a supporting quote, or none.
3. Review: the supervisor reads one step's short answers and quotes, never the record text, and either accepts the step or asks for a redo with a new instruction. A redo reruns the step once on every chunk. An accepted step stays exactly as it was.
4. Aggregation: the supervisor gives the final answer as JSON from the step findings, using the redone findings for redone steps and the original findings for all other steps.

The protocols differ only in which steps go to review:
- Plan once: no steps.
- Check every step: all steps.
- Triggered logprob: steps whose mean of chunk mean log probabilities is strictly below the warmup threshold in Section 3. A step where no chunk gave an answer has no score and is never flagged.
- Triggered agreement: steps where any chunk answer changes across the original instruction and 2 fixed paraphrases.
- Random logprob and random agreement: random steps, the same number per question as the matching triggered protocol (Section 9).

The oracle is not a protocol. It uses the gold answer to find the cheapest set of reviewed steps that makes the final answer correct. It tries sizes 0, 1, 2, then all steps, cheapest first within a size, and skips sets whose redone steps match a set already tried. If no set it tries is correct, the question counts as wrong. Because it uses the gold answer, it is an upper bound for analysis only.

Three reference baselines run outside the shared pipeline and share none of these parts: cloud only, where the supervisor reads the full padded record; local only, where the 27B worker reads the full padded record alone; and MinionS, in its original configuration with its own code.

Each protocol is charged only for the calls it uses. Identical prompts are answered once and reused, whichever protocol asked first. I report two figures. Fresh cost is the new API calls actually made. Protocol accounting cost charges every aggregation a protocol needs at its first call price, even when it was reused. Reuse also happens on eval, because an accepted review changes nothing, so several protocols often send the same final prompt for a question. On warmup, all aggregations after the shared parts cost 24 fresh calls for 27B and 62 for 4B.

## 7. My success margin and my reading rule

Success margin means: how close is close enough for triggered to be called matching check every step, decided before eval, so I cannot move the goalpost after seeing eval results. I decided: 5 points, per worker, not pooled, because workers differ in strength and my proposal lists tests per worker. 5 points is 0.05 in proportions, not 5 percent relative. I considered 7 points and rejected it, because 7 points, 14 questions on eval, is too much to call matching in a clinical task, for a modest cloud cost saving on warmup. The saving is in review calls, not in aggregation alone.

The margin applies to the accuracy difference, triggered minus check every step, with a confidence interval, not to a single point estimate alone. If the interval lies entirely above minus 5 points, triggered is non inferior to check within 5 points. If the interval crosses minus 5 points, the result is inconclusive, not a success, and not a proof of failure. Non significance against zero is not evidence of non inferiority. Formal decision is by Holm adjusted p-value, see Section 6. Interval is descriptive. If Holm and interval disagree, Holm decides, and I will report the disagreement.

Reading rule, with a switch defined now, before eval, so I cannot choose which way to read the results after seeing them. Check counts as better than plan only if its patient bootstrap 95 percent interval against plan lies entirely above 0. Interval method is Section 8: patient bootstrap, 10,000 replicates, resampling 20 patients with all 10 questions together, paired within question, difference is check accuracy minus plan accuracy. If that interval lies entirely above 0, check is better. Otherwise, check is not better, whether the interval includes 0 or lies entirely below 0. That is the switch, no other definition will be used.

If the switch says check is better, then margin versus check is meaningful: triggered matching check within 5 points at lower cost, with the interval rule in this section, is a success for that triggered protocol.

If the switch says check is not better, matching check says nothing about the signal. On warmup, check was below plan on both workers, 27B 19 versus 20, 4B 13 versus 15. Plan once with zero reviews also matches check within 5 points, so a pass on margin alone would not show the signal works. In that case, I will judge success by the fallback in Section 9, triggered versus random control on net, rescued versus broken, and cost saving, not by margin versus check alone.

Can this design detect a good trigger at all? On warmup, yes, in the sense that aggregation does respond to reviews, and no, in the sense that warmup reviews never helped. Evidence: flips changed step answers, separator changed 2 steps on 27B and 23 steps on 4B, and flips changed final answers in 5 cases, all to wrong, breakage 1 on 27B and 4 on 4B. If aggregation were insensitive to reviews, check would equal plan exactly, with 0 breakage, but check broke 3 questions, so aggregation does respond, just in the wrong direction on warmup. The design can detect a good trigger on eval if triggered rescues more than it breaks, net greater than random, or oracle gap greater than 0, see oracle gap below. If none of those happen on eval, the reading is not that the signal failed alone, it is that the review step itself did not rescue, see oracle gap.

Most likely eval outcome, pre-registered reading: check is not better than plan by the switch above, triggered equals plan equals random, net equals 0, oracle rescued equals 0, sweep curve is flat or decreasing with reviews, cost increases with reviews. If that outcome happens, I will conclude: review step is the bottleneck, not signal selection alone, triggered protocols do not beat random, and no threshold in the sweep rescues. I will not re-read that outcome as a success on margin versus check alone, because the switch says check is not better.

Mechanism on 4B warmup, mean numbers: triggered logprob mean reviewed 31 steps. Only 9 of those 31 were steps the supervisor wanted to redo, 29 percent. Random logprob reviewed 31 steps, with 12 redo steps in that set, 39 percent. Overall, 35 of 69 steps were redo steps, 51 percent. Accept review changes nothing, reviewed job is None, original stays, so triggered logprob barely touched answers and stayed equal to plan once. The inverted signal kept it away from risky steps by luck, it did not find steps needing help. I will not count this as support. Random picked more redo steps than the signal, yet accuracy was the same, which is further evidence that warmup accuracy cannot separate signal from chance.

## 8. My intervals, patient cluster primary

My eval questions are grouped by patient: 20 patients, 10 questions per patient, q-indices 3 to 12, sharing the same clinical record. If a patient record is hard, many questions for that patient may be wrong together. Questions for the same patient are not independent, they move together.

I will use patient cluster bootstrap as my primary interval for eval accuracy differences. I will resample 20 patients with replacement, keep all 10 questions for a sampled patient together, paired within question, repeat 10,000 times, compute the accuracy difference each time, and take the interval from that distribution. Seed for this bootstrap is 20261105, distinct from random control seeds. Cost is compute only, no API calls.

Reason for 10,000, not 1,000: strictest Holm cutoff is 0.05 divided by 8, about 0.006. With 1,000 replicates, the p-value can be off by about plus or minus 0.005, enough to flip a pass or a fail. With 10,000 replicates, resolution is 0.0001, and error near 0.006 is about 0.0008, much smaller.

Two sided formula, capped at 1: p equals 2 times the smaller of share of replicates with difference less than or equal to 0, share of replicates with difference greater than or equal to 0. One sided formula for check tests, capped at 1: p equals share of replicates with difference less than or equal to minus 0.05.

Question paired bootstrap interval is reported as sensitivity, not as primary. McNemar is reported as sensitivity, not as primary. For separator AUCs, cluster unit remains question, because steps within a question share that question plan, 1,000 replicates, seed 20261030. Cluster intervals will be wider, because effective sample size is smaller than 200. Wider intervals mean it is harder to claim a significant difference, but that is the true uncertainty. Ignoring clustering makes intervals too narrow.

## 9. My random controls

Random controls are exploratory, not primary, not in Holm. Random pool is all steps of a question, 0 to K minus 1, including steps logprob cannot score, because every step has a review call in the shared log, so a random pick can choose them. One seed is one random draw.

For question number i in shared log order, 0 based, random logprob uses random.Random(20261103 plus i), random agreement uses random.Random(20261104 plus i), sample without replacement, size equal to triggered n_reviews for that question, for the corresponding triggered protocol. If triggered n_reviews is 0, random sample is empty, aggregation is plan once, cached. If triggered n_reviews is K, random sample is all steps, aggregation is check every step, cached.

Warmup random results are in the key table. On both workers, random controls gave the same accuracy as the signals they matched, with the same number of reviews. I will use this comparison on eval to judge whether a signal picks better steps than chance, not just whether it preserves plan.

Fallback criteria, defined now, exploratory, out of the Holm family. For each triggered protocol, per worker, compare it with its random control on net, where net equals rescued minus broken, rescued is plan wrong and protocol correct, broken is plan correct and protocol wrong, over 200 eval questions. Report rescued, broken, and net separately for triggered and for random, not net alone, because net 0 can hide rescue 5 and broken 5 versus rescue 0 and broken 0, which mean different things. Net difference is triggered net minus random net. Patient bootstrap 95 percent interval for net difference, 10,000 replicates, resampling 20 patients with all 10 questions together, paired within question, seed 20261105, same method as Section 8. Net difference divided by 200 equals accuracy difference, because net equals correct count minus plan correct count, so net difference is just accuracy difference in question counts, clearer for small numbers. If the interval for net difference lies entirely above 0, triggered beats random on net. If it includes 0, triggered does not beat random on net. If it lies entirely below 0, triggered is worse than random on net. These fallback comparisons stay exploratory and out of the Holm family, they do not become primary tests after seeing eval results.

Oracle gap, defined now, per worker. Oracle gap equals oracle accuracy minus plan once accuracy, over 200 eval questions, oracle as in Section 2, sizes 0, 1, 2, all-K, cheapest first. Oracle rescued is a count of observed recoveries, and the oracle never breaks a question, so I report the count directly. If it is 0, no review set within the oracle search recovered a wrong answer, and I report the review step as the bottleneck, not the signal. If it is above 0, I report the recovery rate, oracle rescued divided by plan once wrong, with a patient bootstrap 95 percent interval, 10,000 replicates, same method as Section 8, paired within question, and each triggered protocol's distance to the oracle. Oracle rescued equals plan wrong and oracle correct, oracle broken is 0 by construction, because oracle stops at size 0 if plan is correct, so oracle gap times 200 equals oracle rescued count. That means even a perfect signal, oracle, could not help, because reviewed steps plus aggregation did not produce a correct final answer for plan wrong questions, when the count is 0. If the count is above 0, oracle recovers at least some wrong answers, signal could in principle help, and triggered versus oracle distance is meaningful. RQ1 already includes distance to oracle, this makes that item specific: distance is oracle accuracy minus triggered accuracy, plus oracle gap itself. Warmup oracle gap is 0 on both workers, 27B 20 minus 20, 4B 15 minus 15, so warmup already shows review bottleneck on warmup, not just signal failure, and eval will test whether that holds on 200 questions.

## 11. My cost caps, failure rules, and local only eval, final, November 2, 2026

Failure rule, pre-specified. If a question fails to complete, for example an Ollama crash or a failed call after retries, I will rerun that question's shared parts until 200 of 200 questions are complete, for each worker. Attempts and retries are logged, and their cost is counted. Any question still failing after the final attempt before analysis counts as wrong for every protocol of the worker whose run failed, not for both workers. For 27B versus 4B comparisons, I will also report the results without that question. It is reported as failed, not excluded from the failed worker's results, and not counted as correct for any protocol of that worker.

Fallback if eval cannot finish, pre-specified.
